# Coordinated Mr-Clean / TuxedoMan cutover

This is the procedure for a **single approved transition**, not authorization to execute it. The live Mr-Clean development container remains on `bee7e73`. Presence lifecycle fixes are committed in `75ede5e`; validation passed 143 tests and a Release build with zero warnings/errors. No services, live schema, Portal settings or Discord configuration were changed during preparation.

The first approved presence-management deployment retires TuxedoMan's role management in the same maintenance window. A short assignment-disabled diagnostic phase is allowed within that window; no separate observation-only release or long-term coexistence is planned. The existing pause safeguard stays simple: enabled registered presence roles are frozen while management/capture is disabled, including overlapping voice bindings. It does not coordinate independent bots or guarantee safety for unregistered voice roles.

## Exact authorized cutover sequence

Execute only after approval of this whole maintenance window, including the candidate deployment, Portal intent change if required, TuxedoMan stop and rollback actions.

1. **Recheck readiness while services remain unchanged.** Confirm tests/build for the approved commit, a healthy original container/database, private backups and rollback identifiers. Build one uniquely tagged candidate using the existing Docker procedure. Verify source/destination permissions and bot Manage Roles/hierarchy. Preserve avatar, moderation, retention and all role-log configuration. Keep the original image/container for rollback.
2. **Prepare gateway/configuration.** Verify Presence Intent is enabled for Mr-Clean in Developer Portal before requesting it (enable only within approved scope). Keep Server Members Intent and existing Message Content Intent. Preserve all existing production settings, `Discord__GuildId=683633975838769192`, `VoiceLogging__Enabled=true`, ConnectedRoleId `894787914599370803`, reconnect grace 120 seconds and checkpoints 10 seconds. Set `ActivityRoles__ObservePresences=true` and retain `ReconcileSeconds=30` in private runtime configuration. Presence **guild management must remain false**; do not issue the enable command yet. TuxedoMan still manages its existing roles at this point.
3. **Deploy one Mr-Clean candidate, gated.** Gracefully stop/preserve the original Mr-Clean container, then start the candidate using its established network/configuration. Do not restart/replace PostgreSQL. Startup automatically applies `20261017130932_VoiceChannelRules` and `20261017134212_PresenceActivityRules` before Discord login. Check successful migrations, correct guild connection, stable process, database access and no unexpected errors. If migration/startup fails, stop the candidate and restore the original Mr-Clean immediately; TuxedoMan has not been stopped. Do not apply Down migrations.
4. **Verify and stage rules within this same window.** `/voice list` must show the four mappings below with empty activity-role lists. `/activity list` must show guild management disabled; explicitly `/activity enable enabled:false` if needed before proceeding. Use `/activity inspect member:@participant` to verify exact PreMiD names/type/application ID. Register every reviewed alias using `/activity track name:<exact-name> type:Playing role:@ExistingRole` (choose the actual reported type). For an optional application restriction include `application-id:<verified-id>`; otherwise omit it. Configure generic fallbacks with `/activity fallback type:Playing enabled:true role:@Other-Games`, and repeat for Listening/Watching/Streaming using their recorded enable flags and native existing role selectors. These enabled rules are staged under the still-disabled guild switch. Review `/activity list`, routing and role IDs. Do not add shared voice-role bindings yet. Verify no Mr-Clean role mutations occurred. If required mappings or activity observations cannot be verified, stop here and abort/roll back; do not transfer ownership.
5. **Stop TuxedoMan's role management.** Use the recorded operator-approved stop/disable-management procedure. Confirm no in-flight role work remains and its supervisor cannot restart management. Check its status/logs; mere silence or an offline icon is insufficient proof of operational stop. Record the transfer time and final holder inventory. Keep its original configuration/service intact for rollback. VC Roles must remain running. Mr-Clean guild presence management is still disabled until this confirmation succeeds.
6. **Enable Mr-Clean, then adopt.** Run `/activity enable enabled:true confirm-cutover:true`. For each reviewed dedicated automation role run `/activity adopt role:@ExistingRole confirm:true`; for mixed/manual roles use `/activity adopt role:@ExistingRole member:@ReviewedMember confirm:true` for each approved grant. Repeat for Other Games and every enabled transferred category/named role. Adoption records ownership; it does not immediately mutate Discord grants. Bulk adoption requires complete member-cache download and reports an adopted count: compare it with the reviewed inventory, accounting for fresh transitions/new grants acquired during handover. Reconciliation is event-driven, with the configured 30-second retry sweep as a backstop. Inspect warnings and actual convergence; a command acknowledgement is not proof of completed role delivery. Existing unadopted grants are deliberately left alone. Unknown cached presence may retain adopted stale grants until fresh evidence; use `/activity confirm-empty member:@ReviewedMember confirm:true` only after independent inactivity verification, never as a blanket cleanup.
7. **Configure approved shared voice roles.** If the actual Codenames role and activity name have been verified, `/voice edit channel:<native Codenames selector> add-role:@Existing-Codenames-Role`. Verify source ID `1126902663607484476` and that presence rules use the identical role ID. Do not select Connected. Add other voice roles only if individually approved. No new roles are assigned by migrations.
8. **Run the manual acceptance matrix below.** Participants generate real activity/voice transitions. Do not fabricate gateway events or send bot test messages. Check role state, existing role logs and voice destinations, then inspect container stability, database connectivity, active voice state and outbox drainage. Record results and remaining unknown members. No restart is needed for this matrix; any restart recovery exercise must be included in explicit approval.
9. **Close or roll back the window.** Accept the transfer only after the required matrix passes and there are no unexplained permission/API errors or competing role managers. Keep TuxedoMan stopped as the retired manager and preserve its configuration/roles for rollback. Do not remove it from the guild or delete roles. Retain original Mr-Clean rollback artifacts, backups and ownership state. A failed acceptance test follows the phase-specific rollback below; do not leave two active managers as a workaround.

## Manual acceptance matrix

- Start/stop a tracked game and a real PreMiD activity: role appears, then disappears promptly on the first confirmed ending update. Existing unrelated roles stay intact.
- Switch tracked → untracked → no activity: explicit role is replaced by Other Games, then Other Games disappears. Test the reverse switch too.
- Report tracked and untracked activities simultaneously: both applicable roles remain; ending one untracked activity must not remove the generic role while another qualifies.
- Shared Codenames role: test voice only, presence only and both. End presence first, then voice; repeat with voice ending first. Remove the role only after both triggers end. If the binding is not configured, this gate remains untested and requires an explicit operator scope decision before acceptance.
- Go offline with a fresh reported empty list and return: clear/reacquire the presence contribution as appropriate. Do not interpret a startup unknown cache as confirmed empty. Document any holders that require later fresh evidence or reviewed manual confirmation.
- Verify four voice routes and unchanged plain-text joins/embed-only departures, channel switch departure-before-arrival, interruption count including zero, reconnect within 120 seconds and actual connected duration excluding gaps. Rename General Voice only with explicit operator permission.
- Verify actual role changes produce only existing role-change logs. Other Games uses its Annoyinglog route; Connected changes appear exactly once through the restored route while VC Roles still assigns/removes it. Check avatar logging, moderation and other role routing without artificial bot messages. Permission requirements/read-only startup checks alone cannot prove all these live paths.

## Phase-specific rollback

**Before TuxedoMan stops:** stop the candidate before starting the recorded original `bee7e73` container with its original image/environment. TuxedoMan remains the sole presence-role manager. Preserve additive migrations, staged configuration, sessions/outbox and logs. Do not continue if the original bot cannot be restored successfully.

**After TuxedoMan stops or Mr-Clean starts managing:**

1. If responsive, `/activity enable enabled:false` to pause and freeze registered presence roles. Keep rules/fallbacks registered/enabled while paused; untracking/disabling registrations can remove the simple protection. Record/save current rules, transferred grants, ownership/contributions and warnings privately. Remove the newly added shared voice bindings with `/voice edit channel:<native selector> remove-role:@TransferredRole` (or `clear-roles:true` only where every binding was introduced in this window). Do not mass-remove member roles. If commands fail, stop the candidate immediately rather than trying live SQL cleanup.
2. Gracefully stop the candidate, retain it/logs for investigation, and verify it cannot auto-restart before TuxedoMan resumes. Never rely solely on the paused switch to permit two running managers indefinitely.
3. Restore the preserved original **`bee7e73`** Mr-Clean container/image/private configuration, with one instance using the token. It has no voice/activity-role reconciler and ignores the new rule/ownership/contribution tables. Do not substitute an intermediate feature image: those may understand voice ownership but not shared presence contributions. Verify its startup, Discord/database connection and original features. Its old Connected suppression resumes; record that expected rollback limitation. Preserve/drain compatible pending voice payloads according to the existing deployment guide; never purge queues.
4. Once the new role-mutating process is confirmed stopped, restore TuxedoMan's recorded original management settings/service and supervisor policy. Verify its startup reconciliation/current roles and normal activity transitions. Its startup reconciliation may change grants according to its original single-activity semantics; this is the intended rollback behaviour. Existing grants were not deleted merely because management stopped. Dedicated automation grants transfer back operationally; retain Mr-Clean's ownership rows as historical recovery state, not authority to run both managers.
5. Verify one active presence-role manager, original voice/role logging, VC Roles and stable containers. If the original Mr-Clean cannot start, keep the candidate stopped and restore TuxedoMan independently once absence of competing mutations is confirmed; report the Mr-Clean outage rather than restarting both candidates. Do not retry the new release without reviewing fresh holder/configuration state and another approval.

Keep additive tables/migration history and corrected role routes. Do not execute Down migrations, delete Discord roles, clear ownership rows, revoke bot tokens or restore the entire database merely to roll back code. Database damage is a separate explicitly authorized recovery operation. If approved Portal changes need reversal, restore the recorded original settings separately; extra enabled intents in the Portal do not require an emergency change when the old binary does not request them.
